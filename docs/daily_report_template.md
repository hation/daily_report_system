# 日报模板说明

更新时间：2026-06-11

本文档是日报内容优化的优先参考。后续如果还要调整日报结构、章节顺序、措辞、字段展示或摘要策略，必须先更新本文档，再同步修改代码实现和测试。

## 模板优先原则

1. 先在本文档中明确要改的日报结构、展示规则和字段来源。
2. 再修改 `src/processors/data_analyzer.py` 中的分析结果结构。
3. 再修改 `src/formatters/simple_report_formatter.py` 中的格式化实现。
4. 最后更新 `tests/test_data_analyzer_content.py` 和 `tests/test_report_formatter.py`。
5. 验证命令固定为：

```bash
python3 -m compileall -q src tests
python3 -m pytest tests/ -q
python3 -m flake8 src tests
python3 src/main.py --run-daily --env test --test
```

## 当前使用的日报格式

格式名称：`daily_work_summary`

代码位置：

- 分析层：`src/processors/data_analyzer.py`
- 格式化层：`src/formatters/simple_report_formatter.py`
- 入口命令：`python3 src/main.py --run-daily --env test --test`

当前章节顺序：

1. 报告头部
2. 今日工作摘要
3. 按项目看
4. 按主题看
5. 关键产出
6. 需要关注的事项
7. 后续关注与建议
8. 数据概览
9. 报告尾部

## 目标阅读体验

日报应优先回答三个问题：

1. 今天主要在哪些项目上投入了工作？
2. 每个项目或主题具体推进了什么？
3. 有哪些关键产出和需要后续关注的事项？

日报不是统计报表，统计数据只放在最后作为辅助信息。

## 模板正文

```text
============================================================

🧭 **今日工作摘要**
```

## 章节规则

### 1. 报告头部

字段来源：运行时当前时间。

展示规则：

- 标题固定为 `📊 **每日工作分析报告**`。
- 时间格式为 `YYYY年MM月DD日 HH:mm`。

### 2. 今日工作摘要

字段来源：`content_summary.daily_summary`。

生成规则：

- 只写一段话。
- 优先展示前三个主题。
- 如果识别到项目，补充“覆盖 N 个已识别项目”。
- 如果存在关键产出，补充“形成了 N 项可识别产出”。
- 如果存在未完成或异常事项，补充“另有 N 条事项需要后续关注”。

### 3. 按项目看

字段来源：`content_summary.project_groups`。

每个项目展示：

- 项目名
- 工作项数量
- 最多两个主要主题
- 最多两个代表事项

展示限制：

- 最多展示 4 个项目。
- 每个项目最多展示 2 条代表事项。
- 项目名需要归一化，例如把路径型项目名转换成 `headroom`、`daily_report_system`。
- 无法识别时显示 `未识别项目`。

### 4. 按主题看

字段来源：`content_summary.human_summary_items`。

每个主题展示：

- 主题名
- 一句主题总结

展示限制：

- 最多展示 5 个主题。
- 每个主题摘要最多约 150 字。
- 每个主题摘要只能包含最多两个重点事项。
- 禁止直接拼接长描述、完整清单或系统日志。

当前主题包括：

- 日报系统与报告优化
- 代码开发与问题修复
- 文档与项目整理
- 数据源与采集
- 需求沟通与方案设计
- 系统健康检查
- 记忆与项目上下文
- 项目文件活动
- 沟通与会话记录

### 5. 关键产出

字段来源：`content_summary.key_outputs`。

展示规则：

- 最多展示 5 条。
- 每条格式为 `{产出摘要}（{项目名}）`。
- 每条摘要最多约 90 字。
- 优先展示完成、实现、修复、更新、归档、验证、部署等产出型事项。

### 6. 需要关注的事项

字段来源：`content_summary.blockers_or_notes`。

展示规则：

- 没有关注事项时隐藏本章节。
- 已完成事项不应因为标题包含“失败”“错误”等词而被误判为关注事项。
- 未完成事项或明确异常事项才进入本章节。

### 7. 后续关注与建议

字段来源：

- `content_summary.blockers_or_notes`
- `summary_statistics.overall`
- `system_health`

展示规则：

- 优先展示真实后续关注项。
- 没有关注项时展示固定复盘建议。
- 最多展示 4 条。

### 8. 数据概览

字段来源：`summary_statistics.overall` 和 `summary_statistics.averages`。

展示规则：

- 放在报告尾部，作为辅助统计。
- 有值才展示对应字段。
- 不应抢占“今天做了什么”的阅读焦点。

### 9. 报告尾部

字段来源：运行时当前时间。

展示规则：

- 固定展示系统名和生成时间。

## 分析结果字段约定

`content_summary` 当前至少包含：

```python
{
    "daily_summary": str,
    "human_summary_items": [
        {
            "group": str,
            "summary": str,
```

## 内容质量约束

- 优先展示具体工作内容，不优先展示数量统计。
- 项目维度优先于主题维度。
- 主题摘要必须短，避免把原始长文本直接拼进去。
- 系统噪音、上下文压缩提示、运行时提示、知识截止日期等内容必须过滤。
- 飞书消息总长度应保持在 9000 字符以内，常规日报建议控制在 1500-2500 字符。
- 真实推送前先使用测试模式生成报告检查效果。

## 后续优化流程

当需要继续优化日报内容时，按以下顺序执行：

1. 修改本文档中的模板、字段或展示规则。
2. 根据模板差异修改 `data_analyzer.py`。
3. 根据模板差异修改 `simple_report_formatter.py`。
4. 更新或新增测试。
5. 运行验证命令。
6. 生成测试模式日报并人工检查最新报告文件。
