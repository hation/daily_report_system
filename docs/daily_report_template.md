# 日报模板说明

更新时间：2026-06-18

本文档是日报内容优化的优先参考。后续如果还要调整日报结构、章节顺序、措辞、字段展示或摘要策略，必须先更新本文档，再同步修改代码实现和测试。

## 模板优先原则

1. 先在本文档中明确要改的日报结构、展示规则和字段来源。
2. 再修改 `src/processors/data_analyzer.py` 中的分析结果结构。
3. 再修改 `src/formatters/simple_report_formatter.py` 中的格式化实现。
4. 最后更新 `tests/test_data_analyzer_content.py` 和 `tests/test_report_formatter.py`。
5. 验证命令固定为：

```bash
python3 -m compileall -q src tests
python3 -m pytest tests/ -q
python3 -m flake8 src tests
python3 src/main.py --run-daily --env test --test
```

## 当前使用的日报格式

格式名称：`daily_work_summary`

代码位置：

- 分析层：`src/processors/data_analyzer.py`
- 格式化层：`src/formatters/simple_report_formatter.py`
- 入口命令：`python3 src/main.py --run-daily --env test --test`

当前章节顺序：

1. 报告头部
2. 今日工作摘要
3. 按项目看
4. 按主题看
5. 关键产出
6. 需要关注的事项
7. 后续关注与建议
8. 数据概览
9. 报告尾部

## 目标阅读体验

日报应优先回答三个问题：

1. 今天主要在哪些项目上投入了工作？
2. 每个项目或主题具体推进了什么？
3. 有哪些关键产出和需要后续关注的事项？

日报不是统计报表，统计数据只放在最后作为辅助信息。

## 章节规则

### 1. 报告头部

字段来源：运行时当前时间。

展示规则：

- 标题固定为 `📊 **2026年MM月DD日工作总结**`。
- 时间格式为 `报告范围：YYYY-MM-DD HH:mm:ss - YYYY-MM-DD HH:mm:ss`。

### 2. 今日工作摘要

字段来源：`content_summary.daily_summary`。

生成规则：

- **结构要求**：包含3-5个要点，每个要点用自然语言描述
- **内容要求**：
  1. 说明今日工作的主要目的和重点
  2. 描述解决了哪些具体问题
  3. 说明取得了哪些实际进展
  4. 如果有阻塞事项，说明原因和下一步计划
  5. 总结今日工作的核心价值

- **语言要求**：
  - 使用完整的句子，避免技术术语堆砌
  - 突出工作目的和实际价值
  - 让非技术人员也能看懂
  - 避免简单复制原始日志内容

- **生成逻辑**：
  1. 分析工作项的实际目的（解决问题、实现功能、规划方案等）
  2. 按优先级排序，突出最重要的3-5项工作
  3. 用自然语言解释每项工作的实际意义
  4. 总结今日工作的整体进展和价值

### 3. 按项目看

字段来源：`content_summary.project_groups`。

**生成规则**：

- **目的分析**：分析每个项目工作的实际目的和价值
- **自然语言描述**：用完整的句子描述项目进展
- **重点突出**：突出每个项目最重要的2-3项工作
- **价值说明**：说明每项工作的实际意义和成果

**展示格式**：
```
• **{项目名}**：今日主要{工作目的描述}，完成了{具体工作1}、{具体工作2}等{工作项数量}项工作，{价值说明}。

• **{项目名}**：今日主要{工作目的描述}，完成了{具体工作1}、{具体工作2}等{工作项数量}项工作，{价值说明}。
```

**换行规则**：每个项目条目之间必须保留一个空行，避免在飞书或 Markdown 展示中被压成同一段。

**示例**：
```
• **sport项目**：今日主要推进跑步健康监测系统开发，完成了app.py功能优化、训练计划生成工具实现等21项工作，提升了系统的用户体验和数据准确性。
```

### 4. 按主题看

字段来源：`content_summary.human_summary_items`。

**生成规则**：

- **主题解读**：分析每个主题下工作的共同目的
- **价值总结**：总结该主题工作的整体价值
- **自然语言**：用通俗易懂的语言描述
- **重点突出**：突出最重要的2-3项工作

**展示格式**：
```
• **{主题名}**：今日主要{工作目的描述}，重点完成了{重点事项1}、{重点事项2}等{工作项数量}项工作，{价值总结}。

• **{主题名}**：今日主要{工作目的描述}，重点完成了{重点事项1}、{重点事项2}等{工作项数量}项工作，{价值总结}。
```

**换行规则**：每个主题条目之间必须保留一个空行，避免在飞书或 Markdown 展示中被压成同一段。

**示例**：
```
• **代码开发与问题修复**：今日主要解决技术实现中的问题，重点完成了端口检测工具规划、项目稳定性检查等47项工作，为后续开发打下了坚实基础。
```

当前主题包括：

- 日报系统与报告优化
- 代码开发与问题修复
- 文档与项目整理
- 数据源与采集
- 需求沟通与方案设计
- 系统健康检查
- 记忆与项目上下文
- 项目文件活动
- 沟通与会话记录

### 5. 关键产出解读

字段来源：`content_summary.key_outputs`。

**生成规则**：

- **具体产物优先**：优先写清楚产出的文件、功能、测试、提交、计划、结论或决策。
- **可追溯信息完整**：每条必须包含项目、类型、来源和说明。
- **标题可读**：标题必须是人能看懂的产出摘要，不能直接使用短码或低信息标题。
- **说明具体**：说明字段应保留足够细节，让读者知道这项产出到底交付了什么。

**展示格式**：
```
1. **{可读产出标题}**
   - 项目：{项目名}
   - 类型：{可交付产出/决策或方向确认/阶段性进展}
   - 来源：{数据源}
   - 说明：{具体产出内容、文件、功能、测试、提交、计划或结论}
```

**示例**：
```
1. **完成5个Task、推送5个commit到GitHub**
   - 项目：system
   - 类型：可交付产出
   - 来源：trae-cn
   - 说明：完成5个Task、推送5个commit到GitHub、新增9个测试；5个Task全部完成，5个commit已推送到GitHub，新增9个测试全部通过。
```

**展示限制**：
- 最多展示 5 条最有价值的产出。
- 必须让读者能直接看出产出的具体东西是什么，例如文件、功能、测试、提交、计划、结论或决策。
- 禁止使用“解决了相关问题”“实现了实际价值”这类空泛模板话术。
- 禁止把 `B`、`执行`、`相关工作`、`项目分析` 等低信息标题直接作为产出标题；如果说明字段有内容，必须从说明中提取可读标题。
- 每条产出必须展示项目、类型、来源和说明。
- 避免技术术语堆砌，让非技术人员也能看懂。

### 6. 需要关注的事项

字段来源：`content_summary.blockers_or_notes`。

展示规则：

- 没有关注事项时隐藏本章节。
- 已完成事项不应因为标题包含“失败”“错误”等词而被误判为关注事项。
- 未完成事项或明确异常事项才进入本章节。

### 7. 后续关注与建议

字段来源：

- `content_summary.blockers_or_notes`
- `summary_statistics.overall`
- `system_health`

**生成规则**：

- **基于今日工作**：根据今日工作进展提出具体建议
- **实际可行**：建议要具体、可执行
- **价值导向**：说明建议的实际价值和意义
- **自然语言**：用通俗易懂的语言描述

**建议类型**：
1. **技术实现建议**：基于今日技术工作提出下一步实现建议
2. **流程优化建议**：基于工作流程提出改进建议
3. **问题解决建议**：针对今日发现的问题提出解决方案
4. **规划建议**：基于今日决策提出后续规划建议

**展示格式**：
```
• **{建议类型}**：建议{具体建议内容}，这样可以{预期效果说明}。
```

**示例**：
```
• **技术实现建议**：建议明天继续推进端口检查工具的具体实现，这样可以避免项目启动时的端口冲突问题，提高开发效率。
```

### 8. 数据概览

字段来源：`summary_statistics.overall` 和 `summary_statistics.averages`。

展示规则：

- 放在报告尾部，作为辅助统计。
- 有值才展示对应字段。
- 不应抢占“今天做了什么”的阅读焦点。

### 9. 报告尾部

字段来源：运行时当前时间。

展示规则：

- 固定展示系统名和生成时间。

## 内容质量约束

- 优先展示具体工作内容，不优先展示数量统计。
- 项目维度优先于主题维度。
- 主题摘要必须短，避免把原始长文本直接拼进去。
- 系统噪音、上下文压缩提示、运行时提示、知识截止日期等内容必须过滤。
- 关键产出必须说明“产出的具体东西是什么”，不能退化成“通过某事，解决相关问题，实现实际价值”的通用话术。
- 低信息标题如果有有效说明，必须从说明中提取可读标题；如果标题和说明都无信息量，则不进入关键产出。
- 飞书消息总长度应保持在 9000 字符以内，常规日报建议控制在 1500-2500 字符。
- 真实推送前先使用测试模式生成报告检查效果。

## 后续优化流程

当需要继续优化日报内容时，按以下顺序执行：

1. 修改本文档中的模板、字段或展示规则。
2. 根据模板差异修改 `data_analyzer.py`。
3. 根据模板差异修改 `simple_report_formatter.py`。
4. 更新或新增测试。
5. 运行验证命令。
6. 生成测试模式日报并人工检查最新报告文件。
